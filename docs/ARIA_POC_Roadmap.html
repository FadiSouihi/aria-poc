1. Executive summary

The current ARIA robot performs well in its happy path — a single known visitor approaches, is recognized in under 2 seconds, and holds a short cloud-LLM conversation. The manual test campaign, however, shows the design is fragile everywhere else: single-human and group detection are two separate code paths (evaluated once per session, not continuously), identity is never re-verified (so a fast visitor swap inherits the previous person's context), departure is a fixed 20-second face-visibility timer, end-of-utterance is a hard-coded pause timeout, cross-session memory does not recall past topics, a camera crash requires restarting the whole application, and the cloud backend is trivially prompt-injectable.

This roadmap replaces that architecture with a single dynamic perception pipeline in which zero, one, or many people are handled by the same code path — "group mode" stops existing as a mode and becomes emergent scene state — and wraps it in a service-oriented runtime where sessions, identity, and memory are robust first-class concepts. Every capability (detector, tracker, recognizer, STT, TTS, LLM, memory) lives behind an interface registered in a plugin registry, so improvements are config changes, not rewrites, and features can be removed just as easily as they are added.

Proof-of-concept target (verified on this machine): ASUS Vivobook 16 — Intel Core 5 210H (8C/12T), NVIDIA RTX 4050 Laptop (6 GB VRAM), 16 GB RAM, Windows 11. Deployment target: Jetson Orin Nano 8 GB under JetPack 6.x. All model and memory budgets are chosen to fit both platforms; the Resource Governor enforces them at runtime.

Deliverable order: documents first (this report, plus the repository-level ARCHITECTURE.md), then implementation phases 0–7, each ending in a demo-able, testable state. The phase ordering is feature-gated, not date-gated.

Success criteria

  • One code path: 0/1/N people produce identical behavior contracts; no mode flags exist anywhere in the code.
  • Continuous identity: a session is bound to a verified person-track and re-checked periodically; a fast A→B handoff can never transfer A's context to B (fixes NFR-07 Step 4, NFR-01 Step 3).
  • Working recall: a returning visitor is greeted with their last open topic — "Did you find the library last time?" (fixes FUNC-10 Steps 1–2).
  • Natural audio: adaptive end-of-utterance replaces the hard-coded pause timeout; non-directed noise and overheard speech are gated out (fixes FUNC-14 Steps 8, 11, 12).
  • Resource discipline: everything fits the laptop budget; memory returns to idle baseline after sessions (fixes NFR-05 residue).
  • Self-healing: no camera/mic failure requires restarting the application (fixes NFR-03 Step 6); camera tampering is detected (fixes FUNC-05 Step 13).
  • Hardened conversation: system prompt extraction is mitigated by a no-secrets design plus input/output screening (fixes NFR-06).
  • Built on telemetry (new requirement): structured logging and the event timeline exist from Phase 0 — any malfunction must be reproducible from the robot's own logs (§9).
  • Built on tests (new requirement): contract tests, hermetic fakes, and deterministic fixture replays from the first commit, so features that misbehave later are reproduced and isolated in minutes (§10).

4.2 Governor policies (enforced at runtime from Phase 0)

  • Camera pacing: 15 fps while the scene is active (tracks present / session open), 2 fps idle; resolution 1280→640 downscale under pressure. Detection cost tracks scene activity, not wall-clock.
  • Placement: STT runs on GPU by default and is demoted to CPU when VRAM pressure crosses a threshold; local LLM loads only on demand and unloads after a cooldown.
  • Backpressure: all queues are bounded; under overload the governor drops frames, never audio, and never blocks the audio thread behind vision work.
  • Teardown: on session close, per-session objects, caches, and queue buffers are released; a soak test (Phase 5) asserts RSS returns to within ~10% of the idle baseline — the direct answer to NFR-05's +300–400 MB residue.

5.1 End-of-turn detection, three tiers (replaces the hard-coded timeout)

  • Tier 1 — VAD (always on): Silero VAD v5 streams at 16 kHz and segments speech; non-speech events (doors, coughs, footsteps) never open a turn in the first place (FUNC-14 Step 11).
  • Tier 2 — semantic turn decision (default): when VAD reports silence, the buffered turn audio (≤8 s, trailing-aligned) is scored by Smart Turn v3.2 — an open-source, 8 MB int8 CPU model (Whisper-Tiny backbone) purpose-built for "should the agent respond yet?". It distinguishes "I'm looking for… the library" (pause, keep listening) from "…the library." (complete) — the exact FUNC-14 Step 8 failure case — using prosody, not just timing, in 23 languages including Arabic and French.
  • Tier 3 — fallback: if Smart Turn is disabled or unavailable, a configurable silence threshold (default 600 ms) takes over, so behavior never drops below today's baseline. A max-utterance cap (default 20 s) prevents runaway capture (preserves the Step 10 behavior the tests liked).

5.2 Language scope — English-only by decision

Per the project decision of 2026-09-19, multi-language interaction — Arabic, French, and especially Derja — is out of scope for the POC: too unreliable to implement well on this hardware class, and a half-working version is worse than none. The robot interacts in English only; there is no language detection, no session-language prior, no switching logic. Nothing about the architecture forecloses the alternative: Whisper and the LLM remain language-agnostic, and every data contract (Utterance, Session) carries a language field — adding French or Arabic later is a configuration matter (STT model, TTS voices, prompt), not a redesign. Derja specifically is documented as permanently out of scope for this architecture class.

5.3 Identity voting (fixes the false-positive match)

A face match is only provisional until the same embedding wins with margin over the runner-up across ≥N frames (default 3) within a track. The track accumulates an embedding gallery with an EMA centroid, so brief pose/lighting variation does not poison identity. Enrollment is a small tool that captures a gallery per person.

5.4 LLM fallback router

Cloud calls are wrapped with a timeout; on timeout or network loss the router loads the local Qwen3-4B-Instruct-2507 (~2.5 GB Q4; first call pays a load latency, later calls are fast; unloads after a cooldown), answers with a localized "offline mode" notice if needed, and retries cloud afterwards. Guardrail classification can share the runtime with a Qwen3-0.6B/1.7B tier if heuristic screening proves insufficient. This upgrades NFR-03 Step 4 from "technical difficulties" to graceful degradation.

7. Unified detection design

This is the direct answer to the project's core problem: two fragile code paths (single vs group) with one-shot evaluation. The prototype has one pipeline; mode distinctions do not exist.

#Design decisionMechanism
1Sense once, decide continuouslyEvery frame → person detection → tracker → N persistent Tracks. The scene is re-evaluated every cycle, not once per session. A "session" is simply a relationship between the robot and engaged tracks.
2Per-track state machinePRESENCE → NEAR → ENGAGED → DEPARTED, driven by proximity, dwell time, facing/pose, and speech. Replaces the single-person trigger assumption; camera-based presence covers the LiDAR role for the POC.
3Identity binding with ID-lockFace pipeline runs per track (not per frame): detect → embed → gallery vote → PersonIdentity. Once bound, the session is locked to that identity.
4Continuous re-verificationThe bound face is re-verified every N seconds (default 5, configurable) and on suspicion triggers (bbox jump, a new face overlapping the engaged track). If the bound face is gone while a different face occupies the track → session freezes and re-authenticates; context never transfers (closes the NFR-07 Step 4 theft path).
5Multimodal departureDeparture requires face-loss and no voice activity and no recent interaction; any activity resets the absence timer. Replaces the fixed 20 s face-only timer (NFR-01 Step 3) and the "look down = left" failure (FUNC-05 Step 4).
6Group awareness by policySceneManager publishes present/near/engaged people; the Dialogue Manager's AttentionPolicy selects the addressee (configurable: nearest-facing, most-recent-speaker, first-arriver), acknowledges bystanders, and treats A→B handoff as a first-class transition (FUNC-11).
7Tamper & failure awarenessFrame-statistics detector (uniformity/blur/blackout) publishes TamperDetected (FUNC-05 Step 13); DeviceMonitor events drive hot reconnect (NFR-03 Step 6).
Acceptance invariant: for any N = 0, 1, 2, … people in frame, the perception layer emits the same event vocabulary and the same per-track state machine applies. Tests assert behavioral parity rather than separate single/group test suites — the defect class "two code paths diverge" becomes structurally impossible.

8. Sessions & personalized memory

8.1 Lifecycle

  • Open: a track reaches ENGAGED and identity is bound → SessionOpened. Greeting is composed from the profile (name if enrolled; recall content if any).
  • During: raw turns kept in a bounded FIFO (default 6, configurable) plus a running LLM-compressed summary — context survives beyond the FIFO limit, an explicit improvement over the current 5-exchange ceiling.
  • Close: departure confirmed (multimodal, §7) or farewell → the LLM extracts MemoryCards from the conversation: topic, short summary, open/resolved status. Cards are appended to the profile.
  • Re-engage: the RecallComposer injects the most recent and any unresolved cards into the greeting context → "Did you find the library last time?" (fixes FUNC-10 Steps 1–2 for same-day and next-day gaps alike, since cards are timestamped).

8.2 Profile model

Field groupContents
IdentityFace embedding centroid + recent gallery, enrolled name (if any), temporary flag for strangers.
HistorySession list with timestamps, MemoryCards, topics discussed.
PreferencesLanguage, voice preference, opt-out flags.
Biometrics-adjacentVoice-print reference (for gating only), last-seen.

8.3 Privacy & retention

  • Sensitive-ID masking is applied at the policy layer — a regex + context filter over both TTS text and display output — with regression tests covering the trigger edge cases found in NFR-07 Step 1.
  • Session data is wiped on confirmed departure, not only when a replacement session starts — closing the lingering-context gap in NFR-07/FUNC-10.
  • Strangers' temporary profiles auto-expire (default 30 days); any profile can be deleted on request; raw audio is never persisted beyond the active utterance.

9. Observability & logging from day one

Logging is a Phase-0 deliverable, not a retro-fit. The governing rule: any malfunction observed at the robot must be reproducible from its own telemetry — logs plus the event timeline — without re-running the scenario. Four layers:

LayerWhat it capturesHow it is used
Structured logsOne logger per service; every line is JSON carrying ts, level, service, event, session_id, track_id, utterance_id bound automatically as context. Pretty human-readable console mode for development.Failures in aria.audio.stt are greppable without reading vision noise; log levels are set per module from config; every state transition that matters logs one line explaining why.
Event timeline ("flight recorder")The EventBus taps every event into a JSONL timeline; an in-memory ring buffer of the last ~5 minutes is auto-dumped to disk on anomalies (service crash, watchdog restart, governor throttling, tamper detection).Post-incident reconstruction: load the timeline with tools/timeline_view.py and see exactly what perception saw, what the dialogue decided, and when — no re-staging of people or hardware.
MetricsCounters and histograms: frame rate, detection latency, track churn, end-of-turn decision latency, STT real-time factor, TTS synthesis latency, LLM time-to-first-token, VRAM/RAM.Drives the Phase 6 dashboard and the budget assertions (§4); every governor decision is logged together with the metric value that triggered it.
Privacy in telemetryThe same masking policy layer (§8.3) applies to logs and the timeline; IDs and names are redacted by the shared filter; raw audio/video never touches disk except in explicitly recorded fixtures.Debuggability without creating a new data-leak channel — consistent with the NFR-07 posture.
Phase-0 rule of thumb baked into code: every governance decision and state transition (session open/close, identity re-verification, language switch, device loss, fallback activation) emits exactly one log line that, read alone, explains the decision — inputs, thresholds, chosen value.

10. Test-first engineering

The same event-bus boundaries that keep features swappable also make them individually testable. The rule enforced from the first commit: no feature is merged without a test that fails without it. Testing is how the robot stays debuggable months later — when something malfunctions on site, the workflow below reproduces it deterministically.

Test typeMechanismWhat it protects
Contract tests (per service)Each interface (Detector, Tracker, FaceRecognizer, STT, TTSBackend, ChatProvider, MemoryStore) has a contract suite; real and fake implementations must pass the same suite.Swapping a backend cannot silently change behavior; a malfunctioning feature is isolated to one implementation in one step.
Fixture replaystools/record_fixture.py records real camera+mic sessions once (single visitor, group, A→B handoff, occlusion, gaze-down, noisy room); tools/replay.py feeds them deterministically through the pipeline.Full-stack scenarios are reproducible without hardware, people, or cloud — the substrate for debugging future regressions.
Scenario tests (CSV-derived)Each mapped defect row (§14) becomes an expected event sequence over a fixture — e.g., "mid-sentence pause → no response attempt until Smart Turn says complete".The original manual test campaign becomes an executable acceptance suite; old failures resurface automatically if regressed.
Hermetic fakesFakeCamera, FakeMic, FakeLLM (scripted replies + canned latencies), FakeTTS; a "test" config profile wires every source to a fake so the whole stack runs headless.Dialogue FSM, attention policy, memory, and guardrails are unit-testable in isolation with zero network or GPU.
Golden filesTranscripts, identity-vote outcomes, and MemoryCard extractions are pinned to golden files with explicit tolerance flags where nondeterminism is legitimate.Model upgrades show a reviewable behavioral diff instead of surprising users.
Benchmarks-as-testsbench_vision/bench_audio assert the budget thresholds of §4; a soak test asserts RSS recovery (NFR-05).Resource discipline is enforced in CI-lite, not hoped for.

Debug workflow for future malfunctions

Reproduce (fixture replay or auto-dumped timeline) → isolate (per-service contract tests narrow it to one implementation) → fix → the scenario joins the permanent regression suite. Because the failure path is replayable, "it works differently now" disagreements end with evidence, not opinion.

11. Guardrails & robustness

11.1 Prompt-injection defense (NFR-06)

The test campaign showed the cloud backend fully extractable via direct, roleplay, and translation-framed attacks. The prototype assumes cloud models cannot be fully trusted and applies defense-in-depth:

  • No secrets in the prompt: behavioral rules are enforced in code (policy layer), so a successful extraction yields nothing critical.
  • Input screening: heuristic classifier for injection patterns (instruction-override phrasing, role-reset framing, encoded/translation-framed extraction) flags or rewrites before the LLM sees the text.
  • Instruction hierarchy + canary: system prompt includes layered instructions and a canary token; the output filter drops responses containing the canary or policy keywords.
  • Zero agency: no tool, file, or network access from the model — the attack surface stays in-context only, by construction.

11.2 Operational robustness

  • Watchdog self-heal: a crashed camera service is restarted in place; the application keeps running (direct fix for NFR-03 Step 6's "full restart of main.py").
  • Hot device reconnect: DeviceMonitor detects camera/mic re-enumeration and the affected service rebinds without restart.
  • Degradation modes: vision-only (mic lost), audio-only (camera lost/tampered), offline-brain (network lost → local LLM). The robot states which mode it is in, on-screen and aloud.
  • Memory hygiene: bounded queues + teardown + governor (§4.2); a 60-minute mixed-use soak test with RSS-recovery assertion gates Phase 5.
  • Startup correctness: audio devices are selected by config identity (name match with fallback), removing the post-reboot "change audio in/out" manual step seen in NFR-04 Step 1.

Modularity rules (how expansion stays easy)

  • Feature = Service + config entry. Adding a capability: implement Service, declare its config schema and the events it produces/consumes, register in YAML. Removing a capability: disable its config entry (or delete the folder) — nothing else changes.
  • One interface per domain: Detector, Tracker, FaceRecognizer, STT, TTSBackend, ChatProvider, MemoryStore. Improvements arrive as new implementations behind the same interface.
  • Events are the contract: the event registry is documented; adding a consumer never requires touching publishers, which is what keeps perception, cognition, and expression independently evolvable.
  • Profiles over forks: laptop and Jetson differ by config profile (models, placement, defaults), never by code branches.
  • Test tooling is product code: fixture recording/replay exists from Phase 1, so every later phase is validated against identical deterministic scenes.

15. Assumptions, limitations, risks

15.1 Assumptions

  • Internet is available on the laptop for cloud LLM/TTS defaults; the design is fully offline-capable by config (Piper1-GPL + Kokoro + Ollama) for the Jetson target.
  • POC uses the laptop webcam + a headset mic; CameraService abstracts the source (webcam / CSI / recorded file / replay), so the robot's real sensors plug in without re-architecture.
  • The current robot uses a CSI camera + USB mic + LiDAR + screen; all are represented as swappable services in the target architecture.
  • Jetson hardware access comes later; Phase 7 is designed now and executed then.

15.2 Known limitations (documented, not hidden)

  • Multi-language interaction (Arabic, French, Derja) is deliberately out of scope per project decision — English-only POC. Contracts keep language fields so a language can be added later by configuration; Derja is permanently out of scope for this architecture class.
  • Overlapping-speaker separation is not in the POC's first milestone; the system politely requests one-at-a-time speech (the human-appropriate version of diarization-lite).
  • Passive anti-spoofing (photo/screen liveness) is research, not a POC-phase guarantee.
  • Cloud prompt injection can be mitigated, not eliminated — the no-secrets design bounds the blast radius and the residual risk is documented in ARCHITECTURE.md.
